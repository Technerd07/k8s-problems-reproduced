# Kubernetes DNS and `/etc/resolv.conf` Reproduction Lab

This folder contains scripts used to reproduce DNS and routing problems in a manually installed Kubernetes cluster.

The reproduced issue occurs even though direct pod-to-pod communication works through the Calico CNI. A pod such as Alpine can reach Nginx directly by Pod IP:

```bash
curl -v http://<nginx-pod-ip>:8080
```

but access through the Kubernetes Service fails:

```bash
curl -v http://nginx-svc:8080
curl -v http://<nginx-service-cluster-ip>:8080
```

The scripts also cover a related node-routing problem where a host-only interface can become the default-route path and cause external connectivity loss on a manually configured node.

## Expected environment

- A manually installed Kubernetes cluster
- Calico configured as the pod network CNI
- Pods running in the `default` namespace
- CoreDNS installed manually for the cluster
- An Alpine pod and an Nginx pod
- `nginx-svc` exposing Nginx on port `8080`
- Root or sudo access on cluster nodes

The scripts are intended for a manual cluster running in virtual machines, including Oracle VirtualBox host-only networks.

## Files

- `etcresolvconferror.sh` — reproduces and describes the DNS resolution failure seen when pods access a Service by name.
- `runonnode.sh` — inspects the node routing table and attempts to configure a default route on the host-only interface.

Neither script installs CoreDNS, edits the Kubernetes DNS configuration, or creates the test pods and Service.

## Problem reproduced

### Pod networking works

Direct communication between pod IP addresses succeeds through Calico. For example, traffic from the Alpine pod can reach the Nginx pod directly:

```bash
kubectl exec -n default pod/<alpine-pod> -- \
  curl -v http://<nginx-pod-ip>:8080
```

### Service DNS does not work

The same request through the Service name does not return a response:

```bash
kubectl exec -n default pod/<alpine-pod> -- \
  curl -v http://nginx-svc:8080
```

The short Service name depends on entries generated by kubelet in the pod's DNS search configuration, such as:

```text
nameserver <core-dns-service-ip>
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

When DNS resolution is broken or stale resolver configuration is generated, the pod may fail to resolve `nginx-svc` and therefore cannot open the Service address.

### ClusterIP may also be unreachable

If direct Pod IP connectivity works while ClusterIP fails, investigate the Kubernetes Service dataplane in addition to DNS. Validating DNS can distinguish these two failures:

- Short Service name fails, but fully qualified name succeeds: inspect pod `/etc/resolv.conf`, DNS search domains, and ndots behavior.
- Both Service names and ClusterIP fail: inspect Endpoints, Service selectors, kube-proxy, Calico Service routing, and node routing/iptables rules.
- Pod IP and DNS succeed but ClusterIP fails: focus on Service routing rather than CoreDNS.

## DNS configuration generated in pods

A DNS-enabled pod normally receives resolver configuration generated by kubelet. Depending on cluster configuration, it may contain a CoreDNS Service address and cluster search domains similar to:

```text
nameserver <cluster-dns-ip>
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`cluster.local` and `svc.cluster.local` are cluster domain-related search suffixes commonly configured by kubelet. `default.svc.cluster.local` identifies the Service in the pod's namespace (`default`) and cluster domain (`cluster.local`). For example:

```text
nginx-svc
nginx-svc.default
nginx-svc.default.svc
nginx-svc.default.svc.cluster.local
```

These values are normally derived from the cluster domain and Pod DNS configuration supplied to kubelet. Incorrect kubelet DNS settings can result in pods with the wrong nameserver, cluster domain, or search path.

## Inspect DNS from inside a pod

First inspect the pod's resolver configuration:

```bash
kubectl exec -n default pod/<alpine-pod> -- cat /etc/resolv.conf
```

Test short-name, namespace-qualified, and fully qualified Service names where DNS tools are available:

```bash
kubectl exec -n default pod/<alpine-pod> -- nslookup nginx-svc
kubectl exec -n default pod/<alpine-pod> -- nslookup nginx-svc.default
kubectl exec -n default pod/<alpine-pod> -- nslookup nginx-svc.default.svc.cluster.local
```

Test Service connectivity:

```bash
kubectl exec -n default pod/<alpine-pod> -- \
  curl -v http://nginx-svc:8080

kubectl exec -n default pod/<alpine-pod> -- \
  curl -v http://nginx-svc.default.svc.cluster.local:8080
```

## Inspect CoreDNS and the Service

```bash
kubectl get pods -n kube-system -o wide
kubectl get svc -n kube-system kube-dns
kubectl get endpoints -n kube-system kube-dns
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns
```

Check the test workload and Service:

```bash
kubectl get pods -n default --show-labels -o wide
kubectl get svc nginx-svc -n default -o wide
kubectl describe svc nginx-svc -n default
kubectl get endpoints nginx-svc -n default -o wide
kubectl get endpointslice -n default
```

Compare the CoreDNS ClusterIP with the `nameserver` entry in the Alpine pod:

```bash
kubectl get svc -n kube-system kube-dns -o jsonpath='{.spec.clusterIP}{"\n"}'
kubectl exec -n default pod/<alpine-pod> -- cat /etc/resolv.conf
```

Verify that kubelet and CoreDNS use the same cluster domain configuration:

```bash
systemctl status kubelet.service
systemctl cat kubelet.service
kubectl -n kube-system get configmap coredns -o yaml
```

## Node routing checks

`runonnode.sh` is intended to run directly on a cluster node. It inspects routes, and in its intended purpose adds and removes a default gateway on the specified interface. Review both routing output and the script before running it in a virtualized cluster.

List the node routes:

```bash
ip route show
ip route get 8.8.8.8
```

Identify the host-only adapter commonly used with VirtualBox:

```bash
ip -br address
ip route show dev enp0s8
```

If an incorrect host-only route or gateway is selected as the default route, the node may lose internet connectivity. Restore or correct routes with care, for example:

```bash
ip route show
sudo ip route del default via <bad-gateway> dev enp0s8
sudo ip route add default via <correct-gateway> dev <correct-interface>
```

Use routes appropriate to the node. Do not assume that `enp0s8` is the host-only interface or that the gateway shown by the script is valid for every VirtualBox network configuration.

## Running the scripts

Make them executable if needed:

```bash
chmod +x etcresolvconferror.sh runonnode.sh
```

Run the node routing script on the affected node as root or through sudo:

```bash
sudo ./runonnode.sh
```

The DNS reproduction script is intended for the manual cluster environment. Execute it only after reviewing its current behavior:

```bash
sudo ./etcresolvconferror.sh
```

## Diagnostic interpretation

| Observation | Likely area to investigate |
|---|---|
| Direct Pod IP works | Calico pod networking may be healthy |
| Service name returns no address | CoreDNS, pod resolver configuration, cluster domain, or kubelet DNS settings |
| Service name resolves but connection times out | Endpoints, Service selector, kube-proxy, CNI Service handling, or NetworkPolicy |
| Service name resolves to the wrong IP | CoreDNS Service IP, stale cache, or incorrect kubelet/cluster DNS configuration |
| Fully qualified DNS works, short DNS fails | Pod search suffixes and `ndots` behavior |
| ClusterIP also fails | Service dataplane, routing, Endpoint population, or iptables/nftables rules |
| Node loses internet access | Incorrect default route or VirtualBox host-only gateway configuration |

## Common checks

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl get svc -A
kubectl get endpoints -A
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl -n kube-system get configmap kube-root-ca.crt
systemctl status kubelet.service
systemctl status kube-proxy.service 2>/dev/null || true
journalctl -u kubelet.service -n 200 --no-pager
```

Calico status and IP rules can also help identify whether packet routing is the cause:

```bash
ip rule show
ip route show table all
iptables-save
ipset list
calicoctl node status 2>/dev/null || true
```

The scripts document a manually reproduced environment and contain experimental shell logic. Their source code has deliberately been left unchanged; review their output and shell behavior before applying any remediation to a cluster.
